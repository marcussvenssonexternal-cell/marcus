# Content Radar: weekly run

The radar answers four questions each week:

1. What are competitors and adjacent players publishing (blogs, newsrooms, public LinkedIn)?
2. Where are the gaps: topics nobody covers well that Vionlabs has standing to own?
3. What should Arash and the team post (hooks mapped to the five pillars)?
4. What's happening around our events, and who mentioned Vionlabs?

Everything it needs is in `content-engine/`:

| File | What it is |
| --- | --- |
| `config/brand.md` | Positioning, products, ICPs, pillars and voice. Read it first. |
| `config/watchlist.yaml` | Companies to track (blog + LinkedIn), trade press, mention keywords, live page URL |
| `config/events.yaml` | Fallback snapshot of the Notion event calendar |
| `reports/<ISO week>.json` | One file per week; the page is built from these |
| `reports/<ISO week>.md` | The same week as a readable brief (generated by the build) |
| `radar/template.html`, `radar/build.py` | Page template and the build/recover script |

## Steps

### 1. Set up and recover history

- Work out today's date and ISO week (`date +%G-W%V`). The week file is `reports/<week>.json`.
  If it already exists, this is a re-run: overwrite it.
- Read the live page so no past week is lost: `Artifact` with `action: "read"` on the
  `radar_url` in `config/watchlist.yaml`. Then run
  `python3 content-engine/radar/build.py --recover <the saved file path the read reports>`.
- Read the two most recent previous weeks' JSON. You need them to avoid repeating ideas and
  to tell what is new in the competitor feed.

### 2. Events

- Query the Notion Event Calendar (data source `collection://3890081c-16a0-806d-b61d-000b128f5c41`)
  with SQL. Columns: `"Event"`, `"Attendance"` (Going / Tbd / Not Going), `"Priority"`, `"Comment"`,
  `"Attendees"`, `"date:Start Date:start"`, `"date:End Date:start"`.
- Keep events that start in the next 60 days with Attendance Going or Tbd, plus events that
  ended in the last 14 days (status `recent`, for recap content).
- If the Notion connector isn't available, use `config/events.yaml` and say so in `coverage`.

### 3. Research (parallel)

Launch these six research agents in one message with the `Agent` tool (general-purpose).
Give each the brand summary (products, ICPs, pillars), today's date, the window, its slice of
`watchlist.yaml`, and the rules below. The window is "since the last run" (8 days) for what's
new, but let agents pull older context when a company has been quiet.

| Agent | Scope |
| --- | --- |
| Video AI & metadata | watchlist group `video_ai` |
| Discovery & personalization | watchlist group `discovery` |
| CTV ads & context | watchlist group `ctv_ads` plus the ad-trade press |
| Clips, shorts & vertical | watchlist group `clips` plus the vertical / micro-drama conversation |
| Industry trends | `trade_press` sources: hot topics, fresh stats, blind spots |
| Events & mentions | the events from step 2 (agenda, speakers, hashtag, pre-event chatter, hooks) and `mentions` keywords on LinkedIn, press and partner sites |

Web searches are capped per session turn (about 200) and shared by every agent, so give each
agent an explicit budget from `search_budget` in the watchlist and tell it to plan its queries.
In week 43 six unbudgeted agents ran out halfway.

Rules to give every agent:
- At most `search_budget.per_agent` WebSearch calls. Try WebFetch on a source page first; if the
  environment's network policy blocks it (DNS or 403 errors), work from search results, keep
  every dated URL, and say so.
- LinkedIn is login-walled: search with `site:linkedin.com/posts "<name>"` and similar, never
  try to log in, and say the view is partial.
- Never invent posts, dates, quotes or numbers. "Nothing new found" is a valid answer.
- Every claim carries a URL and a date.
- Return: per-company latest items (title, date, URL, one-line argument), cross-cutting themes,
  crowded claims, gaps tied to evidence, and 4–6 idea seeds (hook, pillar, format, source).

### 4. Write the week

Write `reports/<week>.json` following the schema below. The build step turns it into the page
and into `reports/<week>.md`, a readable brief of the same content, so don't write the brief by hand.
Anything you couldn't verify (an award, a quote, a number from one search snippet) goes in
`coverage` and is worded as unconfirmed wherever it appears.

Quality bar for ideas (6–10 per week):
- The hook is the post's first line and states the opinion. It follows the voice rules in
  `brand.md`; none of the banned phrases.
- Each idea cites at least one source it reacts to, and says what Vionlabs can bring
  (a number, a product example, a customer story that is already public, a demo).
- Spread across the five pillars; at least one idea ties to an upcoming event; at least one is
  a contrarian take.
- Don't repeat a hook or angle from the previous two weeks unless there's genuinely new news.
- Mark `"new": true` on a competitor only if it has items that weren't in last week's feed.

### 5. Build and publish

```sh
python3 content-engine/radar/build.py   # validates every week, writes radar/index.html and reports/*.md
```

Fix any problem it reports, then publish with `Artifact`: `file_path`
`content-engine/radar/index.html`, `url` = `radar_url` from the watchlist. Don't pass `icon`.

### 6. Save

Commit `content-engine/reports/` (and any watchlist fixes, such as a blog URL that moved) and
push to the branch this session was given, or to `claude/content-radar` if it wasn't given one.
Never push to `main`. If the push fails, say so and carry on: the published page holds every
week, and the next run recovers them from it.

### 7. Report back

Finish with a short message: the headline, the top three ideas (hook + pillar), events in the
next 14 days, mentions that need a reply, and the page link.
